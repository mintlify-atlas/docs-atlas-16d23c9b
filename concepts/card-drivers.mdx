title: "Smart card drivers: ATR detection and supported cards"
description: "Understand how OpenSC card drivers work, how ATR-based auto-detection selects the right driver, and which card families are supported out of the box."
---

A card driver is a plugin within `libopensc` that knows how to talk to a specific smart card or family of cards. Every card has its own APDU command set, file structure, and security model. Card drivers encapsulate those differences so that higher layers — the PKCS#11 module, `pkcs15-tool`, and application code — can work with any supported card through a uniform API.

## How driver selection works

When a card is inserted into a reader, `libopensc` reads the card's **ATR** (Answer To Reset) — a byte string the card transmits on power-up that identifies its type and capabilities. OpenSC then walks the list of registered card drivers in order and asks each one whether it matches the ATR.

The first driver that claims the card is bound to the `sc_card` object. If no driver matches, OpenSC falls back to the generic default driver, which provides basic ISO 7816-4 file operations without card-specific optimisations.

<Note>
ATR matching is defined per driver using pattern/mask tables. The PIV driver additionally performs application selection (by AID) because multiple physical card platforms can carry a PIV applet.
</Note>

## The default driver

`sc_get_default_driver()` (declared in `src/libopensc/cards.h`) handles cards that match no other driver. It implements generic ISO 7816-4 operations: `SELECT FILE`, `READ BINARY`, `UPDATE BINARY`, `VERIFY` (PIN), and the generic security environment commands. It is enough to browse a card's file system with `opensc-explorer` but does not support card-specific optimisations or PKCS#15 emulation.

## Identifying your card

Before configuring OpenSC, identify exactly which card you have:

```bash
# Print the ATR of the inserted card
opensc-tool --atr

# List all drivers compiled into this build
opensc-tool --list-drivers

# Show which driver OpenSC selected for the current card
opensc-tool --name
```

Example output from `opensc-tool --atr`:

```
3B:9F:96:80:1F:C3:80:31:A0:73:BE:21:13:67:43:20:07:18:00:00:01:A5
```

You can look up ATRs in the [OpenSC ATR database](https://ludovicrousseau.blogspot.com/) or in the `src/libopensc/card-*.c` source files.

## Overriding automatic driver selection

If auto-detection picks the wrong driver, or if you are testing a new card, you can force a specific driver:

```bash
# Force the PIV driver
pkcs11-tool --module opensc-pkcs11.so --card-driver piv --list-slots

# With opensc-tool
opensc-tool --card-driver piv --list-files
```

In `opensc.conf` you can set a per-reader override:

```
# opensc.conf
reader_driver pcsc {
    reader MyReader {
        card_driver = piv;
    }
}
```

## PKCS#15 emulators

Drivers for cards that do not use a native PKCS#15 file layout register a **PKCS#15 emulator** alongside the card driver. The emulator synthesises the PKCS#15 object model — private keys, certificates, PINs — from the card's proprietary file structure.

From the application's perspective there is no difference: `pkcs15-tool --dump` and `pkcs11-tool --list-objects` produce the same output whether data comes from native PKCS#15 files or an emulator.

<Info>
The PIV, CAC, GIDS, nPA, belpic, esteid, and itacns drivers all use PKCS#15 emulation. See [PKCS#15 data structures](/concepts/pkcs15) for a full explanation.
</Info>

## Algorithm capabilities

Each card driver advertises the algorithms it supports by populating `sc_supported_algo_info` structures on the `sc_card` object. OpenSC uses this information to select the correct padding and hashing strategy when the PKCS#11 layer constructs a `sc_security_env` for a signing or decryption operation. If a requested mechanism is not in the card's capability list, OpenSC returns `CKR_MECHANISM_INVALID` before sending any APDU.
